Who is contributing

Headcount rather than event counts: a six-person organisation and a one-person organisation can file the same number of PRs.

Who reviews whom

Review is where organisations actually meet. Cells on the diagonal are organisations reviewing their own PRs; everything off it is cross-organisation effort. Cells always show the PR count — the switch changes what the colour means: by column (the default), where the review an organisation receives comes from; by row, where each organisation directs its own reviewing.

Review outcomes

Whether reviews approve, request changes, or just comment — counted against the organisation giving the review, not the one whose PR it was. Superseded is an approval or change request that a later push invalidated, so the approval count is a floor rather than an exact total.

What contributors get back

How long a PR waits for its first review and for merge, by the organisation that opened it.

Code volume

Totals are dominated by large generated or vendored changes, so the median PR size sits alongside them.

Methodology

Data collected from the GitHub API via PyGithub, covering activity in the 6 months prior to 2026-10-13 across the following repositories: anemoi, anemoi-core, anemoi-datasets, anemoi-inference, anemoi-transform, anemoi-utils.

Bot accounts and automated code agents are excluded from all charts on this page (they remain in results.json).

  • Which organisations get their own series: orgs.json lists the organisations that keep their own colour and legend entry, however small their contribution — a partner with a single PR stays visible, because volume is a poor proxy for how much a contribution matters here. Every other organisation is folded into Other organisations for charting only, and named with its numbers under Smaller contributors. The underlying data is never folded. The turnaround chart is the one exception: medians cannot be pooled, so it shows organisations individually and relies on its own minimum-PR filter instead.
  • Issues: count of issues opened, grouped by the organisation of the issue author.
  • Pull Requests: count of merged PRs where an organisation had at least one contributor. Contributors are identified as: the PR opener, any commit author, and any Co-authored-by: trailer entries in commit messages (resolved via GitHub's noreply address format or a manually maintained email mapping). Each organisation is counted at most once per PR, even if multiple members contributed.
  • PRs Reviewed: PRs an organisation reviewed, counted once per organisation per PR regardless of how many of its people reviewed or how many comments they left, and attributed to the period in which the review was submitted rather than the period the PR was opened. Authors reviewing their own PRs are not counted. This replaces the earlier Total Reviews and Unique Reviews: GitHub files every batch of inline comments as its own review record, so two thirds of those counts were comment batches and a further 30% were self-reviews, which meant the figures tracked commenting style more than review effort.
  • Merged PR Types: the same merged PR counts above broken down by Conventional Commits prefix (feat, fix, refactor, docs, etc.) parsed from the PR title. PRs whose title does not match a known prefix are grouped as other.
  • Who is contributing: distinct people, not events. Someone active in several repositories is counted once. A contributor is anyone credited on a merged PR; a co-author identified only by email address counts as one person via a salted hash of that address. First-time means their earliest merged PR anywhere in Anemoi falls inside this window.
  • Who reviews whom: the same reviews as PRs Reviewed, split by the organisation of the PR's opener, so each cell is a count of distinct PRs. Raw counts differ by orders of magnitude between organisations, so the colour is normalised rather than absolute: by column (the default) each reviewed organisation's cells sum to 100%, showing where the review it receives comes from; by row each reviewing organisation's cells sum to 100%, showing where it directs its effort.
  • Review outcomes: every review submitted in the period by state — the one place submissions are counted individually rather than once per PR, since the question is what verdicts were given — grouped by the organisation of the reviewer who submitted it rather than the organisation whose PR was under review; self-reviews excluded. GitHub records a plain comment as COMMENTED, so it is the most common state by far. Superseded is GitHub's DISMISSED state: when a review is dismissed — most often automatically, by branch protection retiring stale approvals as soon as new commits are pushed — GitHub overwrites the state on the original review, so whether it was an approval or a change request is no longer recoverable from the API. Those reviews therefore appear here rather than under Approved, which makes the approval count a lower bound. In the current data the same reviewer goes on to approve the same PR again in roughly 40% of superseded reviews, which is the signature of the approve, push, re-approve cycle.
  • What contributors get back: medians over PRs merged in the window — measuring merged rather than opened PRs means every PR counted has a complete, observed lifetime. Attributed to the opener's organisation. Only organisations with at least 3 merged PRs are shown, as medians over one or two PRs are noise.
  • Code volume: additions and deletions on merged PRs. A PR credited to several organisations contributes its full size to each, matching how PR counts are attributed. Totals are easily dominated by generated or vendored files, which is why the median PR size is shown next to them.
  • Trends Over Time: each run of the data-collection script archives a dated snapshot under history/. The trend figure plots the per-org totals (summed across all repositories) of each metric against the snapshot date, so you can see how contribution patterns evolve. Note that each snapshot is a rolling 6-month window, so adjacent points share overlapping data.
  • Community health over time: the same snapshots, read for breadth rather than volume. Snapshots archived before these metrics existed are skipped; run python backfill.py --regenerate-existing to recompute every archived snapshot in place. The merge-time panel omits an organisation on dates where it had fewer than 3 merged PRs, so sparse weeks do not show up as spikes.
  • Browse History: each archived snapshot is also rendered as a standalone page showing the data as it was at that point in time.

Organisation attribution is based on a manually maintained mapping of GitHub usernames to organisations which may not be exhaustive.
